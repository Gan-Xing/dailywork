# Signed bill calculation detail and remarks

The signed bill summary is the immutable source of official amounts. A price item now expands into its original Excel calculation rows, including road, side, raw PK, dimensions/formula, and previous/current/cumulative quantities. Blank cells remain null; negative reversals remain adjustments. Subtotals are explicitly separate and must not be added again to detail rows. The UI uses cards in narrow panels and columns when the actual container is wide enough.

This reuses `ValueBillReview` and `ValueBillReviewRecord`. Each imported project/period has one source-checksummed dataset; `data` preserves precise source decimal text, expanded formulas, source cells, row classifications and source-row-to-template-leaf mapping. The legacy rounded `quantity` column is not the source of display values. All template leaves are retained (Agnibilekrou 7: 77 with four unpriced rows; Bondoukou 10: 87 with fourteen unpriced rows); the original 73 signed snapshot price rows remain unchanged. A source row is associated with a specific source template row, rather than a normalized price code that may occur twice.

`FileAssetLink`, with entity `signed-bill-revision` and purpose `calculation-review`, associates the existing Excel asset and frozen revision with the dataset manifest. Reads validate revision/project/period/checksum against the file and dataset. Frozen bill lines, totals and hashes are never edited to attach calculation rows. A changed source must not silently overwrite the existing dataset; it requires an explicit reviewed source-version decision.

GET `/api/value/signed-bills/[id]/calculation-review` requires `value:view`. PATCH requires `value:update`, accepts `{recordId,note,expectedUpdatedAt}`, and changes only the manual remark (maximum 2000 characters). A conditional update prevents overwriting another user's remark; the change and `DETAIL_NOTE_UPDATED` event are saved in one transaction, retaining old/new text and actor. Source notes remain separate. `CALCULATIONS_IMPORTED` records import provenance without reactivating a version.

Billing and construction are separate facts. The new path does not infer construction completion from measured values, zero/blank cells, dimensions, a progress percentage, inventory, or review status. Existing site variation records are shown as comparison candidates with their original units and dates; a READY_TO_MEASURE or MEASURED flag does not establish their coverage by this bill. A quantity in pieces is never subtracted from a quantity in metres. Unsupported completion matches stay pending. Only an independently established completion fact combined with a proven unmeasured quantity may be labelled completed but unmeasured.

No new tables, columns or dependencies are required. A unique-index migration allows separate source workbooks for the same project and period while retaining `key` uniqueness. Old Tanda review records, working measurements, finance cases and original file assets are preserved. Missing companion datasets for other periods are clearly labelled as not imported.

Reviewed omissions and subtotal/unit errors use a narrow correction on the existing record's `source` JSON. `quantityCorrections` identifies the field, source cell, exact original decimal value, corrected value, reason and evidence. `unitCorrection` identifies the original and corrected unit with the same evidence. The DTO validates the original value before applying a correction; invalid or stale corrections fail with a conflict. The original `data`, file checksum, manual remark and signed summary remain intact. The page shows the corrected quantity/unit and its correction explanation. This does not establish physical completion.

Corrections are applied by a controlled, backed-up operation with original-record checks and a `CALCULATION_CORRECTED` audit event in the same database transaction. The event records original/corrected annotations, actor and source checksum. The associated manifest removes only resolved discrepancy messages and retains the resolution history; unresolved source-versus-signed conflicts remain pending. The ordinary remarks PATCH cannot create or alter corrections. A signed bill's quantity or money is never increased just to match an unpriced calculation row.
